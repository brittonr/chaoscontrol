## Campaign journal

`/tmp/cc-kvm/p7/campaign/campaign-journal/` holds `LOCK` and `epoch-0000/seg-00000000.cbor` … `seg-00000011.cbor`. `/tmp/cc-kvm/p7/journal_dump.py` (identical to the p6 script) decoded all 12 segments and printed the record order. The chain was checked by decoding the headers with the same script and computing each segment digest with `b3sum --derive-key 'chaoscontrol.campaign-journal-segment.v1 segment-bytes'`, the `SEGMENT_DIGEST_CONTEXT` in `journal/format/segment.rs`:

- Every header has schema `chaoscontrol.campaign-journal-segment.v1`, epoch 0, and contiguous seq 0–11. Record counts are 6, 2, 7, 2, 7, 2, 7, 2, 7, 2, 3, 1.
- Every `previous_digest` equals the derive-key digest of the previous segment's bytes. Seg 0 chains from zero.
- The final segment digest is `54049d34e165c7f70a8bf33600ce53d1f2aed86f815c1fcdea2b8f1f1bbfd00d`.
- `checkpoint.json` binds `{epoch 0, segment_seq 10, segment_digest 5760897c498bc99e957f7c974890aad1985fef9cd682d5a655fc1b76e3967ad8}`. This is the digest of seg 10, the last settlement segment.

Record order, where k is the number of children admitted in round r:

| Seg | Records |
| --- | --- |
| 0 | GENESIS(epoch 0, seed 42), root MOMENT, `CampaignAdmitted`, ENTRY(0), `CandidatesAdmitted`, `GuidanceAdmitted` |
| 2r+1 (r = 0..4) | SELECTION(round r), `SelectionPublished` |
| 2r+2 | k MOMENT, `ResultObserved`, [k ENTRY, `CandidatesAdmitted`, k `GuidanceAdmitted`], `GuidanceAdmitted` (the decay revision), ROUND(r) |
| 11 | `StopAccepted{reason: SelectionLimitReached, incomplete_search_acknowledged: true}` |

The selections by round are seq 0, 1, 2, 3, and 1. The k values are 1, 1, 1, 1, and 0, which admitted ENTRY 1, 2, 3, and 4 in rounds 0–3. Round 4 admitted no child, so segment 10 holds only `ResultObserved`, `GuidanceAdmitted`, and ROUND. No `PruneFrontier` event appears, because nothing reached `max_frontier` 50. The stop is the CC-D6 mapping of product `completed`.

In the chain, every round's selection segment comes before that round's settlement segment. The live run shows the same order in time, as far as the clocks can resolve it:
- Segment times are ctime on ZFS. They advance in whole-millisecond steps: segs 0 and 1 share one ctime, and all mtimes equal their ctimes.
- Log times are taken when the timestamper reads a line. Each one is therefore an upper bound on when the explorer emitted the line.

Two checks follow:
- Selection before effects: each selection segment's ctime is earlier than the round's first logged effect, `Generated 4 variant schedules`. That line is logged after mutation and before any restore or dispatch.
- Effects before settlement: the round's last VM effect is its last `Incremental snapshot: N dirty pages total` line, which is logged after the last branch ran. The table compares that line with the settlement segment's ctime.

| Round | Selection ctime before first effect | Last VM effect before settlement ctime |
| --- | --- | --- |
| 0 | 66.2 ms | yes, 85.0 ms |
| 1 | 20.0 ms | yes, 11.3 ms |
| 2 | 1.7 ms | not resolved: the line is stamped 0.04 ms after |
| 3 | 2.0 ms | not resolved: the line is stamped 1.05 ms after |
| 4 | 22.3 ms | yes, 9.9 ms |

In rounds 2 and 3 the settlement ctime can trail the true write by up to one coarse tick, and the log stamp can trail the true emission by the pipe read latency. The ordering in those rounds is therefore not resolved by these clocks. These margins show the order of logged effects only. They do not observe KVM ioctls; strace attachment is blocked by `ptrace_scope=1`.

## Evidence class and non-claims

- Evidence class: each run is a bounded VM campaign. It is execution evidence only for the recorded kernel, initrd, binaries, bounds, seed 42, and this host.
- The parity receipt, `frontier-trace.jsonl`, and the Campaign journal are structural decision evidence. They are not VM, fault, assertion, finding, replay, minimization, or release evidence.
- The legacy-diagnostic run is diagnostic rollback output and is marked release-ineligible. It serves only as the parity comparison input.
- No replay, snapshot-backed reproduction, or minimization was attempted. The runs found no bug, so there is nothing to promote.
- Live observations are not claimed to agree between the policies. This covers coverage, child moments, findings, and assertion exercise. KVM repeatability is not established on this host. The spec scenario's "observations agree" is met only by replaying each run's recorded observations through the other policy.
- Uncovered paths: no explore draw occurred (every u ≥ 0.1), and nothing was pruned. These live runs did not exercise the explore-index mapping or `plan_pruning`; the P4 model corpus covers both.
- Only fault-schedule mode ran. Input-tree and hybrid modes, `--workers` > 1, resume, and journal recovery did not run under KVM.
- Publication durability is shown only by the live journal's committed chain and the checkpoint binding. Fault injection of fsync or rename did not run under KVM. The replayed Campaign backend in the checker writes a scratch journal without fsync.
- Time and memory are not measured. Throughput and phase timings in `report.txt` are incidental.
- This smoke does not replace the `nix flake check -L` gate of task 42, which has not run at this pin.
