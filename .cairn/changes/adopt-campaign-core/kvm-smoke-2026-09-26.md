The chain was checked with the same decoder for headers and `b3sum --derive-key 'chaoscontrol.campaign-journal-segment.v1 segment-bytes'` for segment digests (the `SEGMENT_DIGEST_CONTEXT` in `journal/format/segment.rs`):

- Every `previous_digest` equals the derive-key digest of the previous segment's bytes. Seg 0 chains from zero.

Rounds 2 and 4 admitted no child, so segments 6 and 10 hold only `ResultObserved`, `GuidanceAdmitted`, and ROUND. No `PruneFrontier` event appears because nothing reached `max_frontier` 50. The stop is the CC-D6 mapping of product `completed`.

Every round's selection segment comes before that round's settlement segment in the chain. The live run confirms the order in time as far as the clocks resolve it. Segment times are ctime on ZFS, with a coarse clock resolution of 1 ms. Log times are taken when the timestamper reads a line, so each is an upper bound on when the explorer emitted it.

- Selection before effects: each selection segment's ctime is earlier than the round's first logged effect, `Generated 4 variant schedules`, which is logged after mutation and before any restore or dispatch.
- Effects before settlement: the round's last VM effect is its last `Incremental snapshot: N dirty pages total` line, logged after the last branch ran. The table compares it with the settlement segment's ctime.

Live observation equality between the two policies is a non-claim. The parity claim rests on the replay receipt in both directions.

## Evidence class and non-claims

- Evidence class: each run is a bounded VM campaign. It is execution evidence only for the recorded kernel, initrd, binaries, bounds, seed 42, and this host.
- The parity receipt, `frontier-trace.jsonl`, and the Campaign journal are structural decision evidence. They are not VM, fault, assertion, finding, replay, minimization, or release evidence.
- The legacy-diagnostic run is diagnostic rollback output and is marked release-ineligible. It serves only as the parity comparison input.
- No replay, snapshot-backed reproduction, or minimization was attempted. The runs found no bug, so there is nothing to promote.
- Live observations (coverage, child moments, findings) are not claimed to agree between the policies. KVM repeatability is not established on this host. The spec scenario's "observations agree" is met only through replay of each run's recorded observations through the other policy.
- Uncovered paths: no explore draw occurred (every u ≥ 0.1), and nothing was pruned. These live runs did not exercise the explore-index mapping or `plan_pruning`; the P4 model corpus covers both.
- Only fault-schedule mode ran. Input-tree and hybrid modes, `--workers` > 1, resume, and journal recovery did not run under KVM.
- Publication durability is shown only by the live journal's committed chain and the checkpoint binding. Fault injection of fsync or rename did not run under KVM. The replayed Campaign backend in the checker writes a scratch journal without fsync.
- Time and memory are not measured. Throughput and phase timings in `report.txt` are incidental.
- This smoke does not replace the `nix flake check -L` gate of task 42, which has not run at this pin.
