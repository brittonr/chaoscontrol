# Design: Separate KVM Debug-Boundary Scheduling

## Context, Consumers, and Ownership

This is a native spec-only plan, not an implementation or execution receipt. The supplied IRQ diagnostic in `proposal.md` disproves the assumption that one KVM debug exit always means one retired instruction. It does not prove that the proposed coarser boundaries repeat. The first consumer is the first-party Rust/Linux SMP campaign and its persisted debugger on the current KVM host. VMM/sim-core scheduler maintainers own execution semantics and replay maintainers own the continuation/persistence contract.

Inspected reuse points are `crates/chaoscontrol-sim-core/src/scheduler.rs` and `scheduler/core.rs` (`VcpuScheduler`, `ScheduleState`, `ScheduleEvent`, `ScheduleJournal`, `SchedulerSnapshot`); `crates/chaoscontrol-vmm/src/vm.rs` (`VmConfig`, `reserve_guest_progress`, `apply_schedule_action`, poison helpers and watchdog helpers); controller per-round traces/poison; and replay `recording.rs`, `session.rs`, `replay.rs`, and `debugger.rs`. Current instruction fields and strict single-step comments are not already a coarse contract. Accepted strict scheduling requirements remain unmodified.

## Decisions

### 1. Explicit mode and exact units

Add the distinct requested mode `ProgressMode::KvmDebugBoundary`, with a required immutable boundary-profile identity. Strict modes retain retired-instruction units and their existing fail-closed capability checks; an instruction proof failure is never a reason to select the coarse mode. A capability indicating that `KVM_SET_GUEST_DEBUG` succeeds is insufficient for either strict instruction correctness or qualified coarse replay.

The proposed initial profile is `kvm-debug-exit-boundary-v1`. One boundary unit is one validated, committed guest-origin return at an allowed boundary, not a `KVM_RUN` call, host interrupt, injection request, elapsed interval, or count of instructions. The profile's closed table admits KVM single-step Debug exits (with expected debug cause), completed PIO/IO exits, MMIO exits, and architectural HLT exits. The table declares exact handling/normalization for each kind and rejects unsupported exit reasons. Shutdown/terminal failures stop the run and do not gain an invented unit; runnable-set observations and interrupt injection are distinct zero-unit events. Hardware debug breakpoints, host `Intr`/`EINTR`, PMU overflow, and signals cannot be counted as coarse boundaries.

PIO/MMIO exits can require KVM re-entry to complete an operation. A boundary is committed only at the profile's defined settlement point, with completion state captured; an incomplete/pending exit is not a safe snapshot/inspection point. Follow the existing pending-I/O settlement machinery instead of double-counting completion re-entry as a new event. Debug exits caused by that completion must be classified by the profile, not guessed to be an extra guest instruction. Before implementation acceptance, actual KVM probes must establish the complete normalization table; a return whose classification is ambiguous fails closed and poisons after possible progress. Broadening the exit table requires a new profile identity and fresh controls.

Quantum and randomized min/max values in this mode count boundary units. A handler containing arbitrarily many instructions can consume one unit; there is no conversion factor to strict instructions. The scheduler can only choose another vCPU at an accepted boundary or a separately validated architectural runnable-set transition. A target inside a hidden interval is unrepresentable, not rounded to a nearby instruction. Simulation ticks, guest virtual time, boundary positions, and instruction counts remain different coordinates.

### 2. Interrupt-handler atomic regions and delivery limits

An atomic region here means the guest-execution interval between two accepted boundaries: no vCPU switch, snapshot, debugger stop, or newly scheduled shell injection is allowed inside it. If IRQ/NMI/exception entry suppresses TF and the handler has no allowed exit, entry, handler body, return, and any subsequent work before the next accepted exit are one scheduler-atomic interval. If the handler itself produces an allowed exit, that exit splits the interval; this plan does not promise every entire handler is atomic. Do not infer IRET completion or hidden nesting from RIP alone. Rearm guest debug per entry where required without calling hidden work single instructions.

Queue external injection intentions in deterministic order at verified boundaries, binding target vCPU, vector/type, source, sequence and requested boundary. Keep requested injection, KVM-accepted pending state, and observed delivery distinct. In-kernel LAPIC/PIT/IOAPIC delivery, interrupt shadows, IF changes, nested NMIs, exceptions, and fault/interrupt collisions can be invisible within `KVM_RUN`. An injection log does not prove the actual delivery instruction or ordering. Only observable delivery facts may be recorded; unknown delivery points must remain unknown. Snapshot/restore must include available pending interrupt/exception, MP/LAPIC/device, and injection-ledger state or reject the profile if its required state cannot be captured.

Host-clock-driven device injection or timer progression cannot acquire scheduling authority. Audit the PIT/LAPIC/IOAPIC, virtual-TSC, fault-engine and controller paths; admit only a declared clock/device profile whose inputs are explicit and replayable at these units. An unsupported in-kernel delivery source, uncapturable pending state, or ambiguous event cannot be blessed by calling a handler atomic: reject that configuration or mark the attempted replay divergent/nonqualified. The future evidence determines the supported workload/interrupt profile; it must not be broadened from one IRQ probe to general NMI/exception determinism.

### 3. Concrete unit/API cutover, not another scheduler

Reuse `SchedulingStrategy`, seeded ChaCha policy choices, runnable-set checks, stale-state rejection, checked arithmetic, `ScheduleJournal` capacity reservation/commit, pre/post identities, and poison propagation. Reuse the existing selection calculation only after it operates on the declared unit. Do not feed boundaries through `ProgressSource::ExactSingleStep`, `ScheduleEvent::GuestProgress`'s retired-instruction contract, or exact-step remainder arithmetic.

Planned migrations, with every producer/consumer and behavioral fixture migrated together:

| Current API/field | Planned replacement and invariant |
| --- | --- |
| `VmConfig::smp_instruction_quantum`, `SchedulerConfig::quantum`, `ScheduleVariant::quantum_override` | `smp_progress_budget`, `progress_budget`, `progress_budget_override`, using `ProgressBudget::Instructions(u64)` or `KvmBoundaries { profile_id, count }`; reject mixed override/strategy units. |
| `SchedulingStrategy::Randomized { min_quantum, max_quantum }` | Unit-tagged min/max turn budgets; validate same unit/profile and existing exclusive upper bound. Round robin also binds its declared budget unit. |
| `ScheduleState::instruction_progress`, `quantum_boundary`, `quantum`, `exact_step` | A discriminated `ScheduleProgressState`: `Instructions { retired, turn_boundary, quantum, exact_step }` or `KvmBoundaries { observed, turn_boundary, quantum, profile_id }`; boundary state has no PMU remainder. |
| `ScheduleEvent::GuestProgress`, `ProgressSource` | Separate `InstructionProgress` with the existing exact/PMU source, and `KvmBoundaryObserved` containing cumulative boundary count and closed typed exit facts; zero-unit runnable/injection events stay explicit. |
| `VcpuScheduler::remaining`, `exact_step`, `ScheduleAction::EnterExactStep` | `remaining_budget` returns a typed budget; exact-step access/action is instruction-only and rejects coarse use. `Switch` progress/boundary values carry mode/unit/profile rather than untyped instruction implication. |
| `ScheduleState::identity`, `ScheduleTrace`, `SchedulerSnapshot` | New schema/domain identity binds mode, typed units, boundary profile/table, normalized events, policy RNG and delivery ledger; old state identities keep their old meaning. |

Update `VmConfig` serialization, VMM progress-source configuration/entry and `apply_schedule_action`, `SimulationConfig` consumers, branch variants/checkpoint serialization, recorder `RecordedScheduleRound`, replay schedule comparisons, session configuration identity, debugger positions/output, and CLI parsers. Discover all exported callers before implementation; remove superseded field names and old serialization aliases rather than maintain a shim. No generic pluggable progress engine, second policy RNG, or duplicate replay loop is required. Strict instruction accounting and PMU correction remain separate typed branches with unchanged semantics.

### 4. Finite host recovery and permanent poison

Every KVM entry in coarse mode, including SMP and a TF-suppressed no-exit interrupt handler, must have a named finite watchdog deadline and a working thread-targeted interrupt/immediate-exit recovery path. Validate recovery capability before guest entry. A finite outer process supervisor supplies an independently observed kill/reap bound if a worker fails to return; it must classify that attempt as operational failure, never a completed session. A timer being armed is not proof of host recoverability; demonstrate actual recovery with a nonreturning handler.

Host elapsed time, timer cadence, host signal counts, contention, and `Intr`/`EINTR` have no authority to increment boundaries, choose a vCPU, advance virtual time, inject a guest event, or publish a target. A deadline cannot fabricate progress for a stuck handler. If an interruption may have allowed guest work but yields no complete verifiable boundary, abort and permanently poison the VM and any partially mutated controller round. Do not retry that live VM as though no work happened. A no-entry preflight failure may release the reserved journal slot and retry; post-entry uncertainty may not. Preserve partial records as diagnostics only, with no completed round, snapshot, restore, trace-drain-as-success, or verified debugger position. Retry requires a fresh runner and independently admitted checkpoint, not clearing the latch.

### 5. Canonical evidence, persistence, and explicit selection

Bump the schedule-state/trace/scheduler-snapshot versions and canonical BLAKE3 domains; version the containing VM snapshot codec and persisted-session/recording envelopes where their execution descriptor changes (current session schema is 2). Canonical identities include mode, unit, boundary-profile schema and table identity, normalized kind/cause, vCPU/sequence, counters/turn budget, pending exit settlement, known queued/pending delivery state and ledger-prefix identity, plus current policy/runnable/RNG state. Include complete clock/device policy and host/KVM/CPU capability profile in the retained execution descriptor. Host timestamps and signal counts are diagnostic-only and excluded from schedule identities.

Restore requires matching mode/unit/profile/schema and full available pending device/delivery state before mutation. Only fully settled verified boundary snapshots are eligible. Replay and debugger use the same canonical continuation validator, compare actual boundary/delivery observations and fault outcomes, and commit a displayed position only on exact arrival at the requested recorded coordinate. "Exact" target arrival means exact arrival in the explicitly declared boundary/tick coordinate, never an instruction-accurate stop. Incomplete or mismatched evidence disposes of the runner. Counterfactual commands remain labeled counterfactual.

New explicit flags are planned on first-party campaign/run and persisted-session replay/inspect/reproduction entry points: `--smp-progress-mode kvm-debug-boundary` and `--smp-boundary-quantum <count>`. Strict instruction quantum flags remain strict-only, without aliases for the boundary flag. For a persisted session, explicit coarse opt-in must match the admitted retained descriptor; CLI cannot override its budget/profile. Absence of opt-in rejects coarse execution even if the manifest names the mode. A strict request remains strict/rejected, never auto-selected coarse. Unknown modes, mixed units, missing profile identity and mismatched overrides fail before execution. Human-authored bounds/configs remain Nickel-backed; runtime traces/snapshots remain Rust-owned.

No conversion of old strict traces/snapshots into coarse evidence, no defaulting absent mode/units/profile, no compatibility re-export or serde alias. Historical bytes may remain diagnostic with their original identity; unsupported execution schemas reject. Update all callers and existing operator/retention documentation during the later implementation cutover. This package does not change accepted specs, strict tasks, dependencies, or old receipts.

## Verification and Evidence Prerequisites (Not Yet Executed)

Before code changes, capture the supplied strict counterexample and current first-party Rust/Linux SMP/persisted-debugger blockage without rerunning it merely to reconfirm. Run the required affected baselines only when implementation is authorized. Name the reviewed kernel/initrd/workload/host/KVM/CPU/clock-device profile, seeds, topology, quantum, repetition count, simulation horizon, journal/artifact bounds, watchdog and outer teardown deadlines in a retained config. No unexplained numeric defaults or selective removal of failed repetitions.

Portable fixtures must test both unit branches and reject stale state, unit/profile confusion, overshoot/regression, unsupported exits, malformed delivery state, exhausted capacity, and counter overflow. Host events interleaved with identical already-observed guest inputs must leave canonical policy output unchanged; this proves only core isolation, not actual KVM delivery repeatability.

Actual KVM acceptance, queued with pueue, requires all of these paired controls:

1. Repeated identical first-party Rust/Linux SMP campaigns and snapshot-backed replays from the same admitted artifacts, seed, non-default topology and coarse budget. Compare full canonical schedule/delivery/fault traces and selected guest assertions, memory/registers and output at every declared observation horizon. Exercise round robin and seeded randomized boundaries; preserve strict unsupported-host rejection and explicit coarse CLI success as separate outcomes.
2. Boundary microguests: ordinary TF-visible execution, POPF/IRET, IRQ entry/return with hidden handler instructions, handler-internal allowed exits, interrupt shadow/IF deferral, deterministic pending IRQ, nested delivery and selected NMI/exception/fault collisions. Verify observed normalization with actual state observations, not just expected log text. Unsupported delivery paths must reject or remain explicitly unqualified, not disappear from the matrix.
3. A handler that loops with no allowed exit plus a second runnable vCPU: verify no fabricated quantum switch, finite watchdog interruption/host recovery and supervisor teardown, operational classification, permanent VM/controller poison, no usable snapshot/result/position and fresh-runner-only recovery. Also test journal/exit-handler/action failure after possible execution and partial multi-VM rounds.
4. Varied host sleeps, signal injection (`SIGALRM`, unrelated signals, `Intr`/`EINTR`), watchdog cadence and CPU contention under unchanged guest inputs. Completed accepted runs must match the complete control trace; timeout/partial outcomes stay operational failures and cannot be discarded to claim universal success. Host signals never count as units or time. Exercise signal interruption during pending I/O and hidden handler execution.
5. Full persisted lifecycle: coarse campaign finding -> bounded reproduction session -> producer exit -> separate replay and inspect processes -> backward/forward seek across a persisted checkpoint -> compare boundary-coordinate arrival, full canonical suffix and declared memory/register observations. Include queued IRQ/device state and non-default topology/clock/budget, and prove no access to producer memory/default configuration. Seek inside an unobservable region must reject.
6. Isolated corruption/negative CLI copies: wrong mode/unit/profile/schema, forged/reordered/dropped boundary or injection records, tampered counters/pre-post identities, missing snapshot, truncated/corrupt bytes, incomplete settlement, wrong kernel/config/artifact/host profile, checkpoint-prefix drift, unknown schema, strict/coarse mismatch, no explicit opt-in, impossible target and poisoned-runner reuse. Both replay and inspect must reject before machine effects where possible and must never expose an unverified position after partial execution.

A validated retained receipt must bind exact source and executable/artifact bytes, all commands/configs/seeds/repetition outcomes, host capability identities, complete controls, canonical comparator results, snapshots/session paths, operational failures, known unsupported delivery classes and claim horizon. Only actual matched repeated controls for that same admitted cohort can support a bounded debug-boundary replay claim; one successful boot, raw log, injection request, portable fixture, or Cairn gate cannot. Failures remain evidence, not reasons to loosen equality. Even such a receipt cannot prove instruction equivalence, universal interrupt delivery determinism, cross-host portability, or whole-system correctness. Existing `snapshot_backed_reproduced` verdict consumers must not silently equate a coarse claim with a strict-instruction claim; retain mode-qualified claim identity and review every downstream validator before any promotion.

## Alternatives and Risks

Relabeling debug exits as instructions is rejected by the observed IRQ counterexample. Timer-based scheduling or a watchdog-forced guest quantum invents host-authoritative progress. Counting only ordinary I/O exits starves compute loops and hidden handlers; coarse mode instead aborts unobservable nonreturning regions. Whole-handler instrumentation/emulation, kernel installation, and a separate scheduler are outside this plan. The remaining risk is that real KVM/device delivery cannot repeat under the proposed profile; the correct outcome is a failed qualification or narrower explicitly reviewed supported profile with new identity, not a present claim that coarse mode solves determinism.
